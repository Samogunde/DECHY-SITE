The terms overlap, which is why people buy the wrong thing. Here is how to tell them apart.

## Website

A website mainly presents information. Visitors read, browse, watch and contact you. Content is the same for everyone, or changes only slightly.

**Examples:** a company site, a portfolio, a blog, a restaurant page, a landing page for a campaign.

**Strengths:**
- Cheapest and fastest to build
- Best for search visibility
- Easy for non-technical staff to update with a CMS (content management system)
- Low maintenance

**Limits:**
- Little personalization
- No real data processing beyond forms and simple features

## Web app

A web app is software that runs in the browser. Users sign in, see their own data, take actions and get results. It behaves like an app but needs no download.

**Examples:** a booking system, a customer portal, a dashboard, an invoicing tool, a project tracker, an online course platform.

**Strengths:**
- Personal accounts and data
- Complex logic and workflows
- Works on any device with a browser
- One codebase to maintain
- Updates reach everyone instantly

**Limits:**
- Costs more than a website
- Needs testing, security and ongoing maintenance
- Limited access to some phone features compared with native apps

**Typical cost:** {{fact:price.web-development-web-app-from}} to {{fact:price.web-development-advanced-web-app-to}} or more, depending on features. A simple internal tool can cost less. See our guide to [custom software development cost](/resources/cost-guides/how-much-does-custom-software-cost/).

## Progressive web app (PWA)

A PWA is a web app with extra abilities. It can be added to a phone's home screen, open full-screen like an app, work partly offline and send push notifications. It still runs on web technology, with no app store required.

**Examples:** a field service tool used with poor signal, a delivery driver app, a news site with offline reading, an internal staff app.

**Strengths:**
- App-like feel without app store fees or review
- Offline support for key features
- Push notifications on supported devices
- One codebase for all platforms
- Cheaper than building separate native apps

**Limits:**
- Some device features are restricted, especially on iPhones
- Not in the app stores by default, which affects discovery
- Behavior varies between browsers and devices
- Not the best fit for heavy graphics or deep hardware access

**Typical cost:** usually 10 to 30 percent more than a standard web app, depending on offline and notification needs.

## How to choose

Ask these questions in order.

1. **Do users need to log in or save data?** If no, a website is probably enough.
2. **Do they need to do something, such as book, pay, upload or track?** If yes, you need a web app.
3. **Will people use it daily, on a phone, sometimes with bad signal?** If yes, add PWA features.
4. **Do you need advanced phone features such as Bluetooth, heavy camera use or background tracking?** If yes, consider a native app instead. See [native vs cross-platform](/resources/comparisons/native-vs-cross-platform-apps/).
5. **Do you need to be found on Google?** Keep public content on a proper website, even if the app lives elsewhere.

## The combination most businesses end up with

A common setup looks like this:

- **A marketing website** at your main domain, built for speed and search
- **A web app** at an app subdomain or behind a login for customers or staff
- **PWA features** added to the app if mobile use is heavy

Keeping them separate lets each do its job. The website can be updated quickly by marketers. The app can follow a stricter release process.

## Three quick examples

**A dental clinic** wants new patients to find it on Google and book. That is a website with an online booking form. A web app is overkill.

**A training company** wants clients to log in, see their course progress, download certificates and pay invoices. That is a web app, with a marketing website in front of it.

**A cleaning company** wants staff to see jobs, check in on site and upload photos, often in basements with no signal. That is a PWA with offline support, or a simple native app if they need more device features.

Start from what the user must do, not from the technology label.

## Mistakes to avoid

- **Building an app when a website would do.** If nobody needs to log in, you are paying for complexity.
- **Building only a website when you need workflow.** Forms and email chains break once volume grows.
- **Choosing a native app too early.** A PWA or web app can validate demand at lower cost.
- **Ignoring search.** Web apps are poor at ranking, so you still need content pages.
- **Skipping security.** Anything with accounts needs proper authentication and data protection.
- **Underestimating maintenance.** Apps need updates, monitoring and support after launch.

## When to move up

Start with the simplest option that meets your goal. Move up when you hit a real limit:

- Your team answers the same questions by email daily: add a portal or web app
- Customers ask for status updates: add accounts and tracking
- Field staff struggle with signal: add offline PWA features
- Usage on phones is high and engagement is slipping: consider notifications or a native app

## Frequently asked questions

### What is the difference between a website and a web app?
A website mainly shows information. A web app lets users sign in and do things, such as manage bookings, upload files or make payments.

### Is a PWA better than a native app?
Not always. A PWA is cheaper and covers many needs. A native app gives deeper device access and store presence. The right choice depends on your features.

### Can a PWA be in the App Store?
It can be wrapped for app stores with extra work, but the main appeal is that it needs no store at all.

### Do PWAs work on iPhone?
Yes, with some limits that have eased over time. Support for features such as notifications varies, so test on the devices your users have.

### Which is cheapest to build?
A website, then a web app, then a PWA with offline features. Native apps for both iOS and Android usually cost the most.

### Can I start with a website and add an app later?
Yes. Plan the design and data well so the app can reuse content, branding and accounts.
