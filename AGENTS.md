# 1A. DECHY VISUAL BRAND SYSTEM AND BRAND GOVERNANCE

The DECHY visual brand system is part of the master architecture and is a
required source of truth for the website, applications, documents,
presentations, social media, proposals, marketing materials, and future
AI assisted design or development.

The coding agent, design agent, content agent, image generation workflow,
and any future brand work must follow this section. Do not create an
independent visual identity for individual pages or features.

## 1A.1 Approved brand direction

DECHY should look like a real, established global technology company.

The visual identity should communicate:

- maturity
- credibility
- technical competence
- clarity
- precision
- confidence
- human judgment
- practical technology
- international capability
- long term reliability

The visual identity must not look like a generic AI startup, crypto brand,
gaming brand, developer portfolio, generic SaaS template, or futuristic
technology concept site.

The design must not depend on visual trends simply because they are common
in AI generated interfaces.

Do not design for an imagined AI detector. Design for authentic human brand
quality, consistency, evidence, clarity, and restraint.

## 1A.2 Official descriptor

The official DECHY descriptor remains:

**Technology, Software, AI & Digital Solutions**

This descriptor is approved for the brand system.

Do not replace it with:

- Technology. People. Progress.
- Technology & Digital Solutions
- Technology Agency
- Digital Agency
- Software Agency
- AI Agency
- Web Agency
- any other invented tagline or shortened descriptor as the official
  descriptor

The phrase **Technology. People. Progress.** was explored during visual
concept generation but is rejected and must not appear as DECHY brand
copy, logo text, wall graphics, website copy, or marketing material unless
the user explicitly re-approves it for a specific purpose.

The full official descriptor does not need to appear in every logo use.
Use the appropriate logo variant for the available space.

## 1A.6 Color restrictions

DECHY must not use a large rainbow palette.

Do not make gradients a core part of the identity.

Do not use the common AI visual combination of purple, pink, cyan, and
neon blue as a default DECHY treatment.

Do not create separate color systems for individual service pages.

Service categories may use subtle supporting visual differentiation only
when necessary for usability, while remaining inside the master design
system.

The brand should be recognizable even when presented only in black and
white.

Color contrast must meet applicable accessibility requirements.

## 1A.7 Typography system

### Primary heading and brand typeface

**Manrope**

Manrope is the primary typeface for:

- logo supporting typography where appropriate
- H1
- H2
- H3
- navigation
- buttons
- prominent UI labels
- major numbers
- brand headlines
- short interface text

Approved weights may include:

- Light 300
- Regular 400
- Medium 500
- SemiBold 600
- Bold 700
- ExtraBold 800

Do not use every weight merely because it is available. Use weight to
create hierarchy.

### Primary body and reading typeface

**Source Sans 3**

Source Sans 3 is the preferred body and long-form reading typeface for:

- paragraphs
- service descriptions
- blog articles
- case studies
- FAQs
- documentation
- technical explanations
- long-form content
- tables and dense information where appropriate

This two-typeface system separates brand expression from information
consumption while maintaining a human and professional appearance.

### Technical typography

A monospace typeface may be used only for:

- code
- command examples
- technical identifiers
- developer documentation where monospace improves comprehension

Monospace must not define the DECHY brand identity.

Do not use typewriter fonts as brand typography.

Do not use futuristic or sci-fi display fonts.

Do not use decorative fonts.

Do not use fake handwritten fonts as part of the core identity.

## 1A.11 Imagery, photography, AI generation, and visual asset governance

> **AMENDED (AMD-04).** Phase 1 is not limited to diagrams. Use purposeful visual content: original diagrams and technical illustrations, legitimate interface or product visuals, and properly licensed professional imagery where it genuinely improves the page. The agent sources and uses images under the standing authorization in ADR 0002 section 2 item 1 (provenance and license recorded in the asset registry; no per-image owner approval; nothing fabricated as evidence). The source hierarchy and authenticity rules below remain in force.

Images are a required part of the DECHY website experience. The website
must not launch as a text-only technology site. Visual content should make
the brand more credible, explain complex technology, support comprehension,
and give important pages a strong human visual identity.

The image system is part of the master brand architecture. The coding
agent, design agent, content agent, SEO workflow, and AI image-generation
workflow must follow this section.

### Image source hierarchy

Use this priority order when selecting website imagery:

1. Authentic DECHY-owned photography and project visuals
2. Authentic client or project visuals where DECHY has permission to
   publish them
3. Properly licensed professional photography or stock imagery
4. Purpose-built illustrations, diagrams, renders, screenshots, and
   graphics created for DECHY
5. AI-generated imagery for appropriate conceptual or illustrative use

The source and licensing/provenance of managed assets must be recorded.
Never use an image merely because it looks attractive.

### Authenticity and evidence rules

Never use generated or stock imagery to falsely imply:

- a DECHY office that does not exist
- a DECHY employee who does not exist
- a client meeting that did not happen
- a client or project that DECHY did not work on
- a physical location where DECHY has no legitimate presence
- a product feature that does not exist
- a result or achievement that has not been verified

AI-generated people must never be presented as real DECHY staff, clients,
partners, or project participants.

Do not manufacture photographic evidence for case studies, testimonials,
certifications, offices, teams, awards, projects, partnerships, or business
results.

DECHY has no approved public physical-location claim in the master plan.
Therefore, imagery must not create the impression of a specific DECHY
headquarters, branch, or local office.

### AI-generated image policy

AI image generation is allowed and can be valuable, but it is not the
identity of DECHY and must not become the default source of every image.

Appropriate uses include:

- conceptual technology illustrations
- AI and machine-learning concepts
- automation and workflow concepts
- cloud and infrastructure concepts
- cybersecurity concepts
- data and analytics visuals
- software architecture concepts
- editorial article artwork
- abstract technology visuals
- explanatory diagrams
- non-literal hero imagery
- campaign graphics
- conceptual product scenes

AI-generated images must be art directed according to the DECHY visual
system rather than produced from generic prompts such as "modern
technology website image."

Avoid common synthetic visual clichés:

- glowing brains
- humanoid robots shaking hands
- generic holographic dashboards
- random floating code
- neon neural networks
- purple/cyan futuristic scenes
- generic futuristic cities
- decorative circuit boards with no meaning
- random 3D technology blobs
- fake enterprise interfaces
- impossible office scenes
- unrealistic devices
- distorted screens
- unreadable fake interface text
- artificial-looking hands or faces
- generic AI business scenes

When visible text, logos, interface labels, numbers, diagrams, or technical
notation are important, use real HTML, SVG, CSS, or manually authored
graphics instead of relying on an image model to render critical text.

Do not claim that an image is "not AI" or attempt to guarantee that an
image will evade an AI detector. The objective is authentic, appropriate,
professionally art-directed visual communication.

### Real photography direction

When photography is used, prefer:

- natural lighting
- realistic environments
- authentic working situations
- professional but relaxed people
- genuine collaboration
- real technology usage
- restrained composition
- believable workspaces
- natural skin texture
- diverse international representation without stereotypes

Photography should feel editorial, credible, contemporary, and human,
rather than exaggerated corporate stock photography.

### Visual consistency

The website should have one recognizable visual language.

Images should generally use:

- restrained compositions
- realistic lighting
- strong subject hierarchy
- moderate contrast
- natural color treatment
- compatibility with the DECHY palette
- generous negative space when text overlays are required
- consistent cropping behavior

Do not apply heavy filters, excessive color grading, fake film effects, or
random visual styles from page to page.

Do not make every image blue merely because blue is a DECHY brand color.
Brand colors should influence the surrounding design and occasional visual
accents, not artificially tint every photograph.

### Image roles

The content system should support distinct image roles:

- hero image
- service image
- technology image
- industry image
- solution image
- article cover image
- article inline image
- case-study image
- project screenshot
- product screenshot
- architecture diagram
- workflow diagram
- data visualization
- icon or illustration
- social sharing image
- Open Graph image
- favicon/app icon

Each role must have defined aspect ratios, responsive crops, focal-point
behavior, performance targets, and accessibility requirements.

### Image selection and generation workflow

The agent must not randomly generate images while building pages.

For every required image, determine:

1. page/entity
2. image role
3. purpose
4. subject
5. source type
6. licensing/provenance requirement
7. aspect ratio
8. responsive variants
9. focal point
10. alt-text requirement
11. performance budget
12. whether AI generation is appropriate

For AI-generated images, the prompt must be art directed using the DECHY
brand system, page context, intended audience, composition, lighting,
subject, color restraint, aspect ratio, and negative instructions.

Before approval, inspect every generated image for:

- realism
- composition
- visual consistency
- brand compatibility
- subject accuracy
- unwanted AI artifacts
- distorted objects
- incorrect screens or devices
- fake text
- accidental logos
- inappropriate symbolism
- cultural problems
- accessibility
- desktop crop quality
- mobile crop quality

Reject images that look obviously synthetic when the page requires
photographic authenticity.

### Screenshots and product visuals

Use real screenshots whenever showing a real DECHY project, software
interface, dashboard, website, mobile application, or technical
implementation.

If a conceptual interface is shown, make its conceptual nature clear when
there is a reasonable risk that users could mistake it for a verified
client product.

Never make a conceptual UI look like verified client evidence.

Before publishing screenshots, remove credentials, private information,
API keys, internal URLs, confidential data, and other sensitive material.

### Image SEO

Meaningful images must support the wider SEO system through:

- descriptive filenames
- accurate alt text
- captions where useful
- responsive image delivery
- modern formats where supported
- width and height attributes
- appropriate lazy loading
- prioritized loading for critical hero imagery
- correct image dimensions
- compression
- CDN/image optimization where available
- stable URLs
- correct Open Graph images
- image sitemap support where useful
- contextual placement near relevant text

Alt text must describe meaningful visual content and purpose. Do not stuff
keywords into alt text. Decorative images should remain decorative and
should not receive artificial SEO text.

### Image performance

Images must not become a major cause of slow page loading.

The implementation should use:

- responsive srcsets
- appropriate sizes attributes
- AVIF/WebP or other modern formats where supported
- compression
- correctly sized derivatives
- lazy loading below the fold
- prioritized loading for critical above-the-fold imagery
- reserved dimensions to prevent layout shift
- CDN/image optimization where available

Do not place 4K or unnecessarily huge originals directly into ordinary page
components when a smaller optimized derivative is sufficient. Keep the
high-resolution master asset separately in the asset library.

### Image asset library and provenance

The project must maintain a structured image asset library containing, where
applicable:

- asset ID
- filename
- source
- source URL
- creator/owner
- license/provenance
- date acquired or generated
- page usage
- image role
- dimensions
- format
- alt text
- caption
- focal point
- approval status
- replacement or expiry information

Do not scatter untracked images across components or repositories.

### The DECHY visual mix

The website should intentionally combine three visual categories:

**Authentic proof**
Real DECHY work, screenshots, projects, people, and approved evidence.

**Human editorial photography**
Professional real-world imagery that makes the technology company feel
human and credible.

**Purpose-built visual explanation**
Diagrams, illustrations, architecture visuals, and carefully art-directed
AI-generated concepts where they genuinely improve understanding.

This combination is preferred over filling the website with generic stock
photos or making every section an AI-generated image.

### Website image acceptance rule

A page is not visually complete merely because an image has been inserted
into every available image slot.

Each image should do at least one meaningful job:

- establish trust
- explain a concept
- demonstrate real work
- improve comprehension
- support the page story
- create visual hierarchy
- strengthen conversion
- improve editorial quality

If an image does none of these things, omit it rather than adding generic
decoration.

## 1A.14 Motion and interaction

Motion should be subtle and purposeful.

Use animation for:

- navigation feedback
- state changes
- loading feedback
- progressive disclosure
- useful transitions
- small interaction cues

Avoid:

- constant floating elements
- excessive parallax
- glowing animations
- decorative particles
- unnecessary scroll effects
- animation that delays content access

Respect reduced motion preferences.

## 1A.16 Writing and punctuation rules

hyphens only where grammatically appropriate.

Do not allow AI generated copy to introduce these prohibited punctuation
patterns during automated content generation.

# 80A. DECHY AUTONOMOUS ENGINEERING & QUALITY STANDARD

This section is mandatory. The implementation agent is responsible for producing working, validated software, not merely generating source code.

## 80A.1 Implementation ownership

The user is the product owner and reviewer, not the implementation/debugging engineer. The agent is responsible for implementation, configuration, testing, debugging, security hardening, deployment preparation, and verification within the tools and permissions available to it.

Do not instruct the user to edit source code, repair configuration, install dependencies, debug errors, fix broken routes, resolve TypeScript or lint errors, or troubleshoot deployment problems when the agent can perform those actions itself.

## 80A.2 Autonomous error resolution

Do not knowingly present broken work as ready for user review. When an error occurs, diagnose the root cause, implement the fix, rerun the relevant check, inspect the result, and continue until the affected system passes. If a fix introduces another issue, continue resolving the new issue.

Do not stop after the first failed attempt when the problem is technically solvable within the repository or connected development/deployment environment.

The agent must resolve, where applicable:

- build errors
- TypeScript errors
- JavaScript/runtime errors
- lint errors
- test failures
- dependency problems
- broken imports
- broken routes
- broken links
- invalid configuration
- deployment failures
- environment/configuration mistakes
- console errors
- hydration/rendering problems
- responsive layout defects
- accessibility defects
- SEO implementation defects
- structured-data validation errors
- security issues that can be resolved within the project

Only request user intervention when the blocker genuinely requires information, credentials, authorization, an external decision, or an action unavailable to the agent. Explain exactly what is required and why.

## 80A.3 No knowingly broken preview

A preview is a review artifact, not a debugging environment for the user. Do not send the user to a preview that the agent already knows is failing.

Before presenting a preview, verify the affected functionality and the production build. If the preview environment itself fails, troubleshoot and redeploy before asking the user to review it.

## 80A.4 Verification loop

For meaningful implementation changes, follow this loop:

Plan → Implement → Check → Diagnose → Fix → Recheck → Verify → Present

Never treat a command merely returning control as proof of success. Inspect its output and verify the resulting behavior.

## 80A.5 Release gate

Before declaring a meaningful milestone ready for user review, run all relevant checks available to the agent, including as applicable:

1. dependency/install validation
2. type checking
3. linting
4. unit/component tests
5. production build
6. route validation
7. link validation
8. browser/rendered-page validation
9. responsive desktop/mobile validation
10. accessibility validation
11. metadata validation
12. canonical/robots validation
13. structured-data validation
14. sitemap validation
15. image/media validation
16. security validation
17. performance validation
18. deployment validation
19. final smoke testing

The exact checks depend on the technology and milestone. Do not fabricate checks that cannot actually be performed.

## 80A.6 Security ownership

Security is part of implementation quality. Protect secrets, credentials, environment variables, APIs, authentication, authorization, user data, server routes, dependencies, headers, redirects, forms, uploads, and integrations according to the technology being used.

Never commit secrets or private credentials to the repository. Never expose server-only credentials to the browser. Resolve discovered security problems before release when the agent can resolve them.

## 80A.7 Production-quality standard

The standard for DECHY is not “the code exists.” The standard is that the implemented feature works as specified, is maintainable, accessible, performant, secure, search-ready, responsive, and consistent with the DECHY brand and architecture.

Do not use placeholders, fake content, fake proof, fake client information, fake offices, fake team members, fake testimonials, fake statistics, or invented credentials.

Do not leave TODOs or temporary hacks in production paths unless explicitly approved and clearly documented.

## 80A.8 Self-review before user review

Before telling the user a milestone is ready, the agent must review its own work against AGENTS.md and the relevant acceptance criteria. Check both the implementation and the rendered result.

If something is incomplete, fix it before presenting the milestone.

## 80A.9 Honest completion reporting

When reporting completion, state what was actually implemented and verified. Never claim a test, deployment, security review, browser check, or other validation was performed if it was not performed.

If a genuinely external blocker remains, identify it clearly instead of hiding it.

## 80A.10 User review is the final product review, not technical QA

The user's review should focus primarily on whether the result matches the intended business, brand, content, UX, and visual direction. The agent is responsible for performing the technical QA necessary to make that review useful.
